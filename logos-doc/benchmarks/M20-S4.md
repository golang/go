# M20-S4: reuse validated cgo heap spans

This is a default-off implementation candidate under RFC-306 section 3.6.4.
Corrected test-first RED is recorded below. Production GREEN, mutation
controls, full regression, and G6 acceptance remain pending. No speedup or
completed milestone is claimed.

## Contract and proof

The existing unknown-pointer checker first calls `inheap(p)`, then calls
`findObject(p, 0, 0)` to obtain the containing allocation. `inheap(p)` is
exactly `spanOfHeap(p) != nil`; discarding that span forces the second lookup.

The hook retains the validated span. The small `logosCgoPointerObject` helper
uses `span.objBase(p)` only when `logoscgoopt` is enabled. The disabled helper
calls `findObject` and returns both of its results unchanged.

The caller has a live Go allocation. `spanOfHeap` has checked the same
in-use state and bounds that `findObject` would check after locating that
span again. `objBase` computes the same span base plus object index times
element size. The bitmap loop, its complete allocation extent, nested-pointer
pin checks, and non-heap global-range path are unchanged.

This does not make an arbitrary interior pointer refer only to the trailing
bytes of an object. A neighboring unpinned pointer must still be rejected.
The result path also retains the earlier root-pinning check. No scheduler,
callback, C ABI, GC transition, or public API changes are introduced.

## Required validation

The object-code test requires no `findObject` call when enabled, exactly one
when disabled, no out-of-line helper, and one ordinary cgo runtime call.
Runtime attacks cover base/interior addresses, small objects, allocation
headers, large objects, nested pinning, and conservative global extents.

The actual C fixture covers foreign and stack addresses, pinned and unpinned
interiors, and exported-result root/child pinning. Its background collector
provides GC stress; it does not prove collection at a particular interleaving.

Two new checkout-only probes require exact failures and restored GREEN:

1. Invert the experiment guard: the enabled code-generation test must see
   the unwanted `findObject` call.
2. Force a zero object base: the runtime attack must report
   `accepted unknown Go memory containing an unpinned Go pointer`.

CI must rebuild and run the declared runtime and cgo families in normal,
race, and cgocheck2 modes with the experiment off/on; preserve the existing
pointer checks; run direct ASan/MSan and stock-Go fixtures; and complete the
default-short dist suite in both settings. These production gates are pending.

## Performance protocol and limits

`BenchmarkCgoOptSpanLookup` passes a saved unsafe pointer to one unmarked,
void C function per iteration. Its containing allocation has no pointers,
but its unknown-pointer contract still requires classification and scanning.
Void results exclude return-frame specialization; the nil address marker
excludes the pointer-free typed-address shortcut.

Baseline and candidate use the same source, inputs, C ABI, pointer-check
obligations, fixed iteration count, machine, and `GOMAXPROCS=1`. Fast-cgo is
disabled; only `logoscgoopt` changes. Preserve all primary samples, ten
fixed-count Go benchmark samples, and separate CPU profiles. Repeat the
same fixed work in the integration build, and keep the 1.05 threshold.
Report allocation and binary-size observations separately.

`BenchmarkCgoOptSpanReference` changes the C parameter to a pointer-free
typed pointer and removes checking obligations. It is a reference, not a
same-contract lower bound. No current row proves that lower bound or the
baseline/floor admission ratio. Noisy measurements are blocked evidence;
a stable non-win must not be promoted. Even a latency pass does not establish
G6 admission, parity, or a completed milestone.

The helper and hook are below 50 lines and address one repeated lookup, so
G6's single-candidate exception applies only to candidate count.
