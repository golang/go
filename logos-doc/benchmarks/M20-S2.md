# M20-S2: ordinary-cgo return-frame specialization

This record covers the first implementation of [RFC-306](../SPEC.md#36-rfc-306-cgo-compiler-optimization).
The experiment is `logoscgoopt`, independent of `logosfastcgo`, and remains off by default.

## Change and contract

A C function's existing `#cgo nocallback` contract proves that its result frame
stays at the same address until the generated C wrapper returns. The gc
generator can therefore omit two `_cgo_topofstack()` calls and the adjustment
of the result-frame pointer. It does not need the stronger `noescape` contract.

The new predicate is in [`cgoopt_logos.go`](../../src/cmd/cgo/cgoopt_logos.go).
The existing generator takes one hook change. Runtime entry, callback guards,
escape and keepalive treatment, argument/result ABI, errno handling, and
sanitizer hooks remain unchanged. In particular, a valid pinned Go pointer
may still be retained by a C function marked only `nocallback`.

The implementation trusts the existing directive. It does not infer effects
from C bodies. Effect/capture analysis, ABI specialization, call-region
optimization, and cross-language inlining are separate planned stages in
RFC-306, not claims about this patch.

The proof uses the existing runtime state: `cgocall` remains in syscall state
through the C wrapper's result store; without a callback, neither stack
copying nor stack shrinking can move that frame. See
[`cgocall.go`](../../src/runtime/cgocall.go) and
[`stack.go`](../../src/runtime/stack.go). Blocking C functions remain legal.

## CI ASan observer correction

At source commit `ec9798522da6ef45ed11c9841c654e39c113b7e2`,
[CI run 43828826746, job 133169041541](https://github.com/gosuda/LoGOs/actions/runs/43828826746/job/133169041541)
passed the formatting and explicit off/on vet checks, both return-frame
mutation controls, and all off/on normal, race, and cgocheck2 focused suites.
Its first direct sanitizer command, the experiment-off fixture with
`go run -asan .`, then failed at 08:19:32 UTC on 2026-11-16:
`panic: callback did not move the Go stack`.
The full dist and benchmark jobs were skipped after that failure.

This failure exposed a test-observer problem. The compiler's
[escape rule](https://github.com/gosuda/LoGOs/blob/ec9798522da6ef45ed11c9841c654e39c113b7e2/src/cmd/compile/internal/escape/expr.go#L103-L113)
makes a typed-pointer conversion to unsafe.Pointer escape when ASan is enabled.
The fixture therefore observed a heap-allocated marker whose address could not
show stack movement. The compiler's
[ShouldAsanCheckPtr predicate](https://github.com/gosuda/LoGOs/blob/ec9798522da6ef45ed11c9841c654e39c113b7e2/src/cmd/compile/internal/ir/expr.go#L1167-L1171)
respects the function's NoCheckPtr pragma.

The correction moves only those two address observations into a small
`//go:noinline` and `//go:nocheckptr` helper. It converts a valid marker
address to uintptr without reading memory or doing pointer arithmetic.
The scoped pragma prevents the observer itself from forcing the marker onto
the heap. The recursive workload, strict before/after address inequality,
C callback, result/errno checks, pinned retained pointer, and scheduler checks
remain unchanged. The fixture continues to build and execute with ASan.

This is a separate test-only correction, with no production optimization or
benchmark change. Its source has been reviewed against the compiler rules;
a successful direct ASan rerun and the subsequent gates are still pending.
The failed run remains part of the record.

The host is a virtualized Linux 6.18.57 x86-64 environment exposing nine
logical CPUs. `/proc/cpuinfo` reports AMD EPYC 9V45 96-Core Processor; the
process affinity is CPUs 0-8. The guest reports 10,206,472 KiB RAM and no swap.
The model string does not mean 96 cores were available to the benchmark.

- Fork and verified bootstrap: Go 1.27.4.
- C compiler: GCC 14.2.0, Debian 14.2.0-19.
- Timer: hyperfine 2.0.0, three warmups and at least ten measured samples.
- gccgo generation check: GCC Go 14.2.0, Debian 14.2.0-19.

The build cache initially filled its 4.9 GiB temporary filesystem. It was
moved to the workspace disk before the full-suite retry. Package indexing
remained enabled. Timing runs start only after builds and tests have finished;
profiles run separately from timed samples.

## Measurement result: acceptance blocked

**This is a draft candidate, not an accepted G6 optimization or a completed
milestone.** Every complete A/B campaign failed G6's noise check on at least
one side. No speedup ratio, ranking score, or performance pass is claimed.
The implementation remains off by default; that does not waive the gate.

The fixed count was **100,000,000 calls per sample**, with three warmups and
ten measured samples for each binary. Every measured sample exceeded one
second. The first campaign used CPU affinity 8; the next two allowed CPUs
0-8 with `GOMAXPROCS=1`. The latter allowed the scheduler to move the workload
after the pinned run showed substantially more wall-time variation than
CPU-time variation. A third complete campaign followed the temporarily stable
candidate window in the second campaign. All samples, including the outliers,
are retained in [the raw evidence](M20-S2-evidence.jsonl).

| Run | Median (s) | Standard deviation (s) | Minimum (s) | Maximum (s) | SD / median |
|---|---:|---:|---:|---:|---:|
| baseline-01 | 3.933 | 1.149 | 2.819 | 6.149 | 29.2% |
| candidate-01 | 4.215 | 1.162 | 2.748 | 6.453 | 27.6% |
| baseline-02 | 3.518 | 1.929 | 2.737 | 8.570 | 54.8% |
| candidate-02 | 3.059 | 0.178 | 2.673 | 3.266 | 5.8% |
| baseline-03 | 4.093 | 2.860 | 3.509 | 12.967 | 69.9% |
| candidate-03 | 4.008 | 5.727 | 3.034 | 20.774 | 142.9% |

G6 requires SD / median at most 20% before scoring. The second campaign's
candidate alone passed that check, but its matching baseline did not. It is
not paired with a baseline from another campaign. CPU time is retained in the
raw records for diagnosis and does not replace the preselected latency metric.
No candidate was selected for promotion, so integration timing is deferred
until a reliable baseline and candidate can be measured.

The generated-code and size observations are independent of this latency
blocker. On linux/amd64 with GCC 14.2.0:

| Observation | Baseline | Candidate |
|---|---:|---:|
| Stack-top helper calls in the measured C wrapper | 2 | 0 |
| Measured C wrapper machine-code bytes | 44 | 19 |
| Complete benchmark executable bytes | 5,556,016 | 5,555,480 |
| Scalar benchmark allocation bytes per operation | 0 | 0 |
| Scalar benchmark allocations per operation | 0 | 0 |

The executable includes multiple eligible wrappers; its 536-byte reduction is
not attributed solely to the measured function. These observations establish
code-generation and size changes, not a latency improvement.

The separate Go benchmark cross-check used the same count for ten repetitions
per side. Its median was 26.08 ns/op for the baseline and 24.53 ns/op for the
candidate, with zero allocation bytes and zero allocations in every sample.
These secondary results do not override the invalid primary campaigns or
establish the required post-integration acceptance result.

Separate CPU profiles attributed 87.64% of baseline samples and 84.19% of
candidate samples cumulatively to `runtime.cgocall`. The measured path is hot,
and the ordinary runtime transition remains in place. Profile runs are not
included in the latency samples.

For a native-call comparison, the existing `BenchmarkFloorCall` calibration reported
4,805 ns for 2,000 native C calls, or 2.4025 ns per call. The ordinary-cgo
calibration/reference ratio is `32.59 / 2.4025 = 13.565`. This is an optimistic
native-call reference, not a proven latency floor for the ordinary-cgo contract,
which retains runtime transitions. It cannot turn an unreliable A/B baseline
into an accepted measurement. The same-contract G6 lower bound remains
unestablished.

## Reproduction

Build the fork first with `./make.bash` from `src`, set `GOROOT` to this checkout,
put its `bin` first on `PATH`, and use `GOTOOLCHAIN=local`. Set `GOCACHE` to a
filesystem with enough space for the experiment and instrumentation variants.
Use separate output directories for the baseline, candidate, and integration.

```sh
export GOMAXPROCS=1
export GOEXPERIMENT=nologoscgoopt,nologosfastcgo
variant=baseline
N=100000000
out="$PWD/../.outline/optimize/M20-S2/reproduce-$variant"
mkdir -p "$out"
go test -p=1 -c -o "$out/workload.test" cmd/cgo/internal/testlogos

# Use the fixed N recorded with the results for both builds.
hyperfine --warmup 3 --min-runs 10 --export-json "$out/timing.json" \
  "taskset -c 0-8 '$out/workload.test' -test.run='^$' -test.bench='^BenchmarkCgoOptNocallback$' -test.benchtime=${N}x -test.benchmem"

taskset -c 0-8 go test -p=1 -run='^$' -bench='^BenchmarkCgoOptNocallback$' \
  -benchtime="${N}x" -count=10 -benchmem cmd/cgo/internal/testlogos

taskset -c 0-8 "$out/workload.test" -test.run='^$' -test.bench='^BenchmarkCgoOptNocallback$' \
  -test.benchtime="${N}x" -test.cpuprofile="$out/cpu.out"
```

Repeat with `variant=candidate` and `GOEXPERIMENT=logoscgoopt,nologosfastcgo`.
The CPU set above matches this host; record a suitable, identical set for both
sides on another host. Repeat the integrated candidate only after valid
measurements establish a viable candidate. Do not profile timed samples or
compare different iteration counts. Report allocation and binary-size
measurements independently of latency.
